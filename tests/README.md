# API Testing with Playwright — Student Guide 🎓

A hands-on, **3-level** course in API testing, built on top of this framework's
shared [`ApiHelper`](../src/utils/ApiHelper.ts). Target API:
[**Restful Booker**](https://restful-booker.herokuapp.com/apidoc/index.html) — a
free, public practice API for hotel bookings. No signup needed.

> **The idea:** the *same* CRUD scenarios are written three times, each with more
> reuse than the last. Read them in order and you'll feel *why* each abstraction
> exists — instead of being handed the final version and told to trust it.

---

## 1. What is API testing (30-second version)

A UI test drives a browser. An **API test** skips the browser and talks straight
to the server over HTTP — send a request, assert the response. It's faster, less
flaky, and tests the contract your front-end (and other services) depend on.

Every API test asks three things:
1. **Status code** — did the server accept it? (`200`, `403`, `404` …)
2. **Body** — is the JSON shape and data correct?
3. **Side effect** — did the resource actually change? (re-read it and check)

## 2. The one Playwright concept you need: `request`

Playwright gives every test a built-in `request` fixture — an
[`APIRequestContext`](https://playwright.dev/docs/api/class-apirequestcontext).
It's an HTTP client with `.get() .post() .put() .patch() .delete()`:

```ts
import { test, expect } from '@playwright/test';

test('hello API', async ({ request }) => {
  const res = await request.get('/booking');   // GET https://restful-booker.herokuapp.com/booking
  expect(res.status()).toBe(200);
  const body = await res.json();
});
```

**Why does `/booking` work without the full URL?** Our
[`playwright.config.ts`](../playwright.config.ts) defines an
`api-restful-booker` project that presets the `baseURL` and the JSON headers:

```ts
{
  name: 'api-restful-booker',
  testDir: './tests',
  use: {
    baseURL: 'https://restful-booker.herokuapp.com',
    extraHTTPHeaders: { 'Content-Type': 'application/json', Accept: 'application/json' },
  },
}
```

So every spec in `tests/` runs under that project and can use relative paths.

## 3. Run it

```bash
npm install                                   # one-time
npm run test:booker                           # ALL booker specs (this folder)

npx playwright test tests/01-raw-request      # just Level 1
npx playwright test tests/02-api-helper       # just Level 2
npx playwright test tests/03-fixtures-e2e     # just Level 3

npm run test:report                           # open the HTML report
```

Credentials default to the publicly-documented `admin / password123`. Override
in `.env` (`BOOKER_USER`, `BOOKER_PASS`, `BOOKER_URL`) — see
[`.env.example`](../.env.example).

## 4. The three levels

### Level 1 — `01-raw-request/` · raw `request`, nothing else

The baseline. You write every header and parse every body by hand, so there's
no magic to misunderstand.

| File | Teaches |
|------|---------|
| [`get-all-bookings.spec.ts`](01-raw-request/get-all-bookings.spec.ts) | `GET /booking`, then a filtered `GET /booking?firstname=…` |
| [`get-booking.spec.ts`](01-raw-request/get-booking.spec.ts) | `GET /booking/{id}` + the `404` path |
| [`create-booking.spec.ts`](01-raw-request/create-booking.spec.ts) | `POST /booking` |
| [`update-booking.spec.ts`](01-raw-request/update-booking.spec.ts) | `PUT /booking/{id}` — fetch a token by hand, send it as a Cookie, + the `403`-without-token path |

```ts
// Level 1: the auth dance is fully visible
const auth = await request.post('/auth', { data: { username: 'admin', password: 'password123' } });
const { token } = await auth.json();

await request.put(`/booking/${id}`, {
  headers: { Cookie: `token=${token}` },   // <-- Booker wants a Cookie, not Bearer
  data: updatedBooking,
});
```

### Level 2 — `02-api-helper/` · the shared `ApiHelper`

Same scenarios, but raw calls go through [`ApiHelper`](../src/utils/ApiHelper.ts).
Watch the specs get shorter and **typed**:

```ts
import { ApiHelper } from '../../src/utils/ApiHelper';

const api = new ApiHelper(request);
const res = await api.post('/booking', payload);          // body is the 2nd arg
expect(api.isSuccess(res)).toBe(true);                    // no more `status() >= 200 ...`
const body = await api.parseJsonResponse<CreateBookingResponse>(res);  // typed!
```

What `ApiHelper` buys you: convenience verb methods, automatic `?query` building
from a `params` object, a typed `parseJsonResponse<T>()`, an `isSuccess()` 2xx
check, and a `callApiWithRetry()` for flaky/polled endpoints.

### Level 3 — `03-fixtures-e2e/` · fixtures + a real journey

The professional setup. Two upgrades:

**(a) The token is generated by a fixture.** No spec calls `/auth` anymore —
[`src/fixtures/booker.fixture.ts`](../src/fixtures/booker.fixture.ts) does it once
and hands you `bookerToken` + a ready `bookingApi`:

```ts
export const test = base.extend<BookerFixtures>({
  bookingApi:  async ({ request }, use) => { await use(new BookingApi(request)); },
  bookerToken: async ({ bookingApi }, use) => { await use(await bookingApi.auth()); },
});
```

**(b) A domain class hides the endpoints.** [`src/api/BookingApi.ts`](../src/api/BookingApi.ts)
wraps `ApiHelper` so specs read like sentences: `createBooking()`,
`updateBooking(id, payload, token)`, `deleteBooking(id, token)`.

**(c) An end-to-end chain.**
[`booking-crud.e2e.spec.ts`](03-fixtures-e2e/booking-crud.e2e.spec.ts) runs ordered
steps that share one `bookingId`:

```ts
import { test, expect } from '../../src/fixtures/booker.fixture';

test.describe.serial('Booking lifecycle', () => {
  let bookingId: number;
  test('create', async ({ bookingApi }) => { /* … */ });
  test('update', async ({ bookingApi, bookerToken }) => { /* … */ });
  test('delete', async ({ bookingApi, bookerToken }) => { /* … */ });
});
```

`describe.serial` = run in order, and if a step fails, skip the rest (a *delete*
test is meaningless once *create* broke).

Test data comes from [`src/testdata/booking.data.ts`](../src/testdata/booking.data.ts)
(`buildBooking()` using faker), so every run sends fresh data but you can pin any
field for a deterministic assertion: `buildBooking({ firstname: 'E2E' })`.

## 5. Restful Booker cheatsheet

| Verb | Path | Auth? | Notes |
|------|------|-------|-------|
| POST   | `/auth`         | no  | `{username:"admin",password:"password123"}` → `{token}` |
| GET    | `/booking`      | no  | array of `{bookingid}`; filters: `firstname/lastname/checkin/checkout` |
| GET    | `/booking/{id}` | no  | full booking; missing id → `404` |
| POST   | `/booking`      | no  | returns `{bookingid, booking}` |
| PUT    | `/booking/{id}` | **yes** | full replace; token as `Cookie: token=<t>` |
| PATCH  | `/booking/{id}` | **yes** | partial update |
| DELETE | `/booking/{id}` | **yes** | success status is **`201 Created`** |

### ⚠️ Three quirks that trip everyone up
1. **Auth is a Cookie, not Bearer.** Send `Cookie: token=<token>` — *not*
   `Authorization: Bearer <token>`.
2. **DELETE returns `201`**, not `200`/`204`.
3. **Bad login returns `200`**, with `{ "reason": "Bad credentials" }` in the body
   — assert the body, not the status.

## 7. Troubleshooting

- **First call is slow / times out.** Restful Booker runs on a free Heroku dyno
  that sleeps. The first request after a cold start can take 5+ seconds — re-run,
  or warm it with `curl https://restful-booker.herokuapp.com/ping` first.
- **`403 Forbidden` on PUT/PATCH/DELETE.** You forgot the `Cookie: token=…`
  header, or the token expired — fetch a fresh one.
- **`500` on POST.** Missing `Content-Type: application/json` (the project sets
  this for you; only an issue if you override headers).
